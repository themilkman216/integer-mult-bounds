## Findings

### 1. Cheap screen (task step 1): zero gain, exactly, for every dispatch

All priced per-provider quantities in #2322 are identical for `gauge44` and `extra`, verified at five independent layers (`scripts/screen.py`, `SCREEN.json`; re-derived in `verify.py`):

- `data/PLAN.json` provider registry: `actual_paid_profile` `{1:2335, 2:512, 3:426, 4:120, 5:38, 8:8}`, ordered `widths` (434 entries), `ports`, `centers` and per-orientation program hashes all equal; only `directory` and artifact hash fields differ.
- `data/SPEC.json` providers: `expected_profile`, `complete_contract.paid_profile`, `complete_contract.local` (per-orientation events/macros/primitives/prefix/wrappers), `expected_local`, `program_hashes`, adapters/primitive-bound/compiler all equal.
- `BASELINE-CONTRACT.json.gz` (the pinned #2312 supplier): paid `{1:2343, 2:504, 3:422, 4:124, 5:42, 8:8}` for **both** providers, ordered 438-width lists equal.
- #2322's shipped strict invoice (`evidence/full-replay/…/PREFIX-AND-INVOICE.json`): both providers' `paid_profile` and per-orientation `local` blocks equal, and `selected_calls` order equals `data/PLAN.json` order.
- Literal recount: `generate_words.paid_profile()` (climbs/cut copies from the word fields, not the registries) returns the same paid profile and width inventory `{4:33, 5:9, 7:38, 8:114, 9:240}` for `words/base.json.gz` and `words/extra.json.gz`, and for the pinned **#2312 source words** it returns the common `{2343, …}` profile (blobs taken from local `refs/upr/2312` only after their sha256 matched both `generate_words.SOURCE_WORDS` and `UPSTREAM-2312.json`). The two #2322 words are distinct circuits (12 differing `B` gates, 4 differing `warps`); only their priced histograms coincide.

Since `owners_check` reads the provider only through (i) the ordered width list (idle) and (ii) the paid profile (per-call sum), the identity `H(dispatch) = idle + 666·paid_common` holds for every dispatch as exact integer arithmetic. Executed confirmation (`SCREEN.json`): #2322's own `verify.owners_check` — full window/family/width/offset legality over all 289044 rows — was run fresh for shipped 417/249, 665+1 retaining (8,73), 665+1 retaining (3,65), 665+1 retaining the first gauge key (2,33), all-`extra` 666, all-`gauge44` 666, and a 222/444 mod-3 mix. Every run returns the identical `H = {1:1576979, 2:340992, 3:292195, 4:79937, 5:27958, 7:87, 8:5328, 12:1, 21:1, 48:24545}` (rank mass 4816512, deficit 23680), equal to `CLAIM.json`'s profile.

Exact moments (`vendor/fine_moment.py` directed enclosures, the engine and grid settings of #2322's `verify.py`): at the CLAIM native endpoint lower `0.0016970602962588368950279736213908681182` the enclosure lies below 1 (`F−1 ≈ −7.57e-41` at 30-digit display; exact Fractions in `SCREEN.json`), at the upper endpoint (last digit 3) above 1, reproducing the shipped bracket; at `b = κ₂₃₂₂ = 1697060296258836/10¹⁸` the enclosures for the shipped dispatch and for 665+1 are **identical Fractions** (`F−1 ≈ −2.588e-18`). The moment gain, and hence the κ gain, is exactly zero. **Task step (2) is therefore not triggered**: there is no candidate to carry through the strict/endpoint/outer chain, and no conditional κ different from 0.001697060296258836 exists for this dispatch move. Running that chain on a 665+1 data copy would re-derive the same endpoint and the same outer κ by construction (it could still fail on non-priced bindings; see *Open next questions* 1).

### 2. Why the 3D lever is absent here: #2312 equalised the paid profiles

On #2269 the lever was real: gauge44 paid `{1:2351, 2:501, 3:414, 4:129, 5:42, 8:8}` vs extra `{1:2339, 2:509, 3:418, 4:125, 5:42, 8:8}`, a per-call difference `{1:+12, 2:−8, 3:−4, 4:+4}` of rank mass zero whose moment at #2269's endpoint favoured `extra` (Track 3D, `PRIOR-3D-README.md` Finding 3). [#2312](https://github.com/CrocSwap/integer-mult-bounds/pull/2312) (Jeremy Kothe) removed that asymmetry as a side effect of its own improvements, in its README's words: an *exact frame refit of both borrowed words* (42 gauge44 frames, 30 extra frames) and the *two helper-donor kernels at pivots 518 and 506 on both words*, after which a single "local profile {1:2343, 2:504, 3:422, 4:124, 5:42, 8:8}" is stated for both. #2322's four-handoff delta `{1:−8, 2:+8, 3:+4, 4:−4, 5:−4}` is likewise applied to both words by `generate_words.py`, which asserts the common `PROFILE = {2335, …}` for each. The priced midpoint is already what an optimal dispatch would approach on #2269, and here it is attained at every call simultaneously — dispatch has nothing left to optimise. (The same is true on #2312 itself, whose 417/249 counts are likewise priced-neutral.) The pinned #2312 runtime even encodes this fact in its negative controls: `assembly_controls.py` has explicit branches for "equal partner profiles (e.g. after a frame refit): the substitution would be the identity" and "identical partner programs" (hash-verified quotations in `ADMISSIBILITY.json`).

### 3. Admissibility of the retained gauge44 call (task step 3, code-level)

This section is a **code analysis of hash-pinned text**, not an executed strict replay of a 665+1 candidate (none was made; §1). Hash discipline (`scripts/admissibility.py`, `ADMISSIBILITY.json`): local `refs/upr/2312` is `6a05b1bb`, a later head than #2322's pin `fb76f799`, so every quoted #2312 file (`replay.py`, `code/witness.py`, `code/bind_providers_portable.py`, `code/assembly_controls.py`, `new/BORROW-PROVIDERS.json`) was used only after verifying its sha256 against #2322's `UPSTREAM-2312.json`. Files whose later-head bytes differ from the pin (`audit_mixed.py`, `code/audit_allcold.py`, `code/invoice_allcold.py`, `code/assemble.py`, `code/emit_allcold.py`, `freeze_spec.py`, `independent_core.py`, `new/SPEC.json`) are **not** quoted for pinned claims; a direct fetch of the pinned supplier was attempted and failed (`fetch_suppliers.py --supplier 2312`, HTTP 403 from the API in this environment), which is recorded as a limitation in §5.

**Which checker forces one retained gauge44 call? The bind stage of the pinned `replay.py`, which #2322's `delta_replay.py` copies verbatim ("Use the exact PR2312 verifier runtime") and runs in both discovery and strict modes.** `replay.py` hardcodes `--provider gauge44=<base local> --provider extra=<native-extra/local>`; `code/bind_providers_portable.py` asserts `set(dirs) == set(PIDS)` where `code/witness.py` defines `PIDS = sorted(set(DISPATCH.values()))` from the candidate SPEC; in strict mode witness also asserts `set(PROVIDERS) == set(PIDS)`, and its `partner()` (used by substitution controls) asserts `len(PIDS) > 1`. A 666 all-extra dispatch therefore still fails — now already at `bind`, before `emit/audit/invoice/assembly` — exactly as all-extra failed on #2269 in Track 3D, though the first failing stage there was identified via `audit_mixed.py` (a file that differs from the pin here and is not needed: the bind assertion is upstream of it and hash-pinned). Note the nuance maintainers may care about: pinned `assembly_controls.py` itself *does* contain a single-provider branch (`len(PIDS)==1` drops the four partner-only controls and keeps the direct ones), i.e. parts of the #2312 runtime anticipate a one-provider dispatch. That branch is unreachable through the shipped `replay.py` driver because `bind` (and the hardcoded two-provider `independent` invocation) bind both providers regardless of dispatch. Admitting 666 would be a *checker/driver change*, not a data change — and on #2322 it would be priced-identical anyway.

**Which single call? Priced: any of the 249. Partner controls: an even-stage one — 142 qualify; (8,73) is one of them, not unique.** Orientation is bound per call as `forward` iff the stage is even (`bind_providers_portable.py`; all 666 calls satisfy it). Pinned `assembly_controls.py` builds two mutants by searching from the first call of each provider: `wrong_selected_call` needs a call of the *other* provider whose stage has the same parity as the first call of `P`, and `moved` needs one with the same orientation (the same condition, by the parity law). The first selected call overall is `extra`, stage 0, forward (#2322 invoice order = PLAN order, checked). If the sole retained gauge44 call were odd-stage/backward, both searches for `P = extra` would come up empty and `next()` would raise `StopIteration` inside mutant construction — the strict run would break rather than cleanly reject the mutant. A sole retained call must therefore be even-stage/forward *for this checker code as written*: 142 of the 249 shipped gauge44 calls qualify, 107 (odd-stage/backward) do not (`verify.py` tamper control T6 mirrors this on (3,65)). The Track-3D retained call (8,73) — the sorted-last shipped gauge44 key, stage 8, forward, time 665, already gauge44 in #2322's shipped dispatch — satisfies it. No rule we found in the pinned files singles out (8,73) among the 142; its retention is the 3D convention, not a #2322 requirement.

So maintainers can judge intent precisely: a 665+1 data copy would be a relabelling that (a) changes no priced or finite-invoice quantity (§1), (b) keeps the bind/witness both-providers rules and the assembly partner controls runnable with (8,73) retained, per the mirrored predicates, and (c) would still require the same data/SPEC refreezing exercise as any dispatch change (provider counts are pinned in the shipped SPEC; `delta_replay.py` rebuilds them by discovery). It would **not** be an improvement to #2322, and this package does not propose it as one.
